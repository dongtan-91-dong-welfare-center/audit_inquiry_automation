# 아키텍처 결정 기록 요약

## 1. 개요
본 문서는 금융거래조회서 키인 자동화 시스템을 개발하는 과정에서 발생한 주요 기술적 의사결정을 요약한 문서입니다. 프레임워크 선정부터 핵심 데이터 처리 로직에 이르기까지, 대안 기술과의 비교 및 최종 채택 사유를 기록하여 향후 유지보수 및 고도화 시 참고 자료로 활용합니다.

## 2. 주요 기술 스택 선정

### 2.1. PDF 처리 라이브러리 선정 (ADR-001)
* **결정 사항:** `pdfplumber` 채택
* **대안 및 기각 사유:** `PyMuPDF`
  * `PyMuPDF`는 처리 속도와 성능 면에서 우수하나, AGPL 라이선스를 따르고 있어 상용화 또는 기업 내부 시스템 도입 시 법적 리스크(소스 코드 공개 의무 등)가 존재합니다.
* **채택 사유:** `pdfplumber`는 MIT 라이선스로 법적 제약 없이 자유롭게 사용할 수 있으며, 문서의 이미지 변환 및 레이아웃 분석에 충분한 성능을 제공합니다.

### 2.2. 프론트엔드 및 UI 프레임워크 선정 (ADR-002)
* **결정 사항:** `Streamlit` 채택
* **대안 및 기각 사유:** `React`, `Django` 등 전통적인 웹 프레임워크
* **채택 사유:** 본 프로젝트는 복잡한 UI/UX보다는 PDF 업로드, 파이프라인(전처리-OCR-후처리) 구동, 결과물(엑셀) 다운로드라는 명확한 단방향 데이터 흐름을 가집니다. `Streamlit`은 Python 스크립트만으로 데이터 파이프라인 결과를 빠르게 화면으로 구성하고 프로토타이핑할 수 있어 개발 생산성 측면에서 압도적으로 유리합니다.

## 3. OCR 엔진 변천사 및 최종 결정

문서의 텍스트를 추출하는 핵심 엔진인 OCR 프레임워크는 한국어 인식률과 표 구조 파악 능력을 검증하기 위해 여러 차례의 도입 및 변경 과정(ADR-003 ~ ADR-006)을 거쳤습니다.

1. **최초 도입 (ADR-003):** `PaddleOCR`
   * **사유:** `pdfplumber`만으로는 스캔본 문서의 텍스트 추출이 불가능하여 OCR 도입이 필수적이었습니다. 초기 검토 시 한국어 및 복잡한 표 인식 성능이 가장 우수하여 채택되었습니다.
2. **1차 변경 (ADR-004):** `EasyOCR`로 전환
   * **사유:** `PaddleOCR`의 복잡한 의존성 문제로 인해 환경 구축 및 유지보수에 어려움이 발생했습니다. 성능이 유사하면서도 의존성 관리가 훨씬 수월한 `EasyOCR`로 임시 전환하였습니다.
3. **2차 변경 (ADR-005):** `Tesseract`로 전환
   * **사유:** 동일한 샘플 조회서를 바탕으로 `PaddleOCR`, `EasyOCR`, `Tesseract` 3종의 엔진을 비교 테스트한 결과, 해당 샘플 기준으로는 `Tesseract`가 가장 높은 정확도를 보여 채택되었습니다.
4. **최종 결정 (ADR-006):** `PaddleOCR`로 회귀
   * **사유:** 다양한 형태의 **실제 스캔본**을 대상으로 실증 테스트를 진행한 결과, 노이즈가 있거나 해상도가 낮은 실무 환경에서는 `Tesseract`의 성능이 기대에 미치지 못했습니다. 실전 인식률이 가장 높은 `PaddleOCR`로 최종 회귀하여 파이프라인을 확정하였습니다.

## 4. 데이터 처리 및 아키텍처 구조 결정

### 4.1. 페이지를 초과하는 다중 표 병합 로직 (ADR-007)
* **문제 상황:** 금융상품이나 대출거래 내역이 많아 하나의 표가 2장 이상의 페이지에 걸쳐 분할 인쇄되는 경우, 이를 독립된 표로 인식하는 문제 발생.
* **결정 사항:** OCR 처리 결과를 딕셔너리로 구조화할 때, **이전 페이지 하단 표의 속성 개수와 현재 페이지 상단 표의 속성 개수를 비교**하는 로직을 도입했습니다. 속성 개수와 레이아웃이 일치하면 동일한 표가 이어진 것으로 판단하여 데이터를 하나로 병합합니다.

### 4.2. OCR 엔진 출력 데이터 구조 표준화 (ADR-008)
* **문제 상황:** `PaddleOCR`, `Tesseract` 등 OCR 프레임워크마다 반환하는 데이터의 형태(좌표 배열 방식, 신뢰도 위치 등)가 다름. (ADR-003~006의 잦은 엔진 교체로 인한 코드 수정 소요 발생)
* **결정 사항:** 시스템 내부 파이프라인이 특정 OCR 프레임워크에 강하게 결합되는 것을 방지하기 위해, **어떤 엔진을 사용하든 동일한 규격(`[텍스트, [x1, y1, x2, y2], 신뢰도]`)으로 정규화하여 후처리 모듈로 전달**하는 인터페이스 표준화 작업을 적용했습니다. 이를 통해 향후 더 나은 OCR 모델이 등장하더라도 `ocr_engine.py`의 어댑터 부분만 수정하여 쉽게 교체할 수 있습니다.
